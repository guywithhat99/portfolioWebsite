# How two wires carry that

----

## The problem two wires have to solve

One wire for data, one for a clock, and possibly several chips listening.

They need to agree on when a message starts, which chip it is for, and when it ends.

----

## The bus

<img src="content/img/i2c-bus.svg" alt="Arduino and sensors all on the same SDA and SCL lines">

----

### The two wires

| Wire | Carries |
|---|---|
| **SDA** | the data, one bit at a time |
| **SCL** | a clock, so both ends agree when each bit counts |

On the Uno these are fixed. **SDA is A4, SCL is A5.**

----

### Why those two and nothing else

Every pin you have used so far was driven by the processor running your code. `digitalWrite` is an instruction, so any pin will do.

I2C is not done by your code. There is a separate circuit inside the chip that generates the clock, shifts the bits out, and watches for the ACK.

<p class="sub">That circuit is wired to two specific pads on the silicon. Those pads come out at A4 and A5.</p>

----

### What that buys you

<div class="two">
<div>

The processor hands over a byte and gets on with something else.

The hardware clocks it out at the right speed on its own.

</div>
<div>

It also means the two pins are spoken for.

<code>pinMode</code> and <code>digitalWrite</code> on A4 or A5 will fight the I2C hardware.

</div>
</div>

<p class="sub">Most peripherals on a microcontroller work this way. A fixed block of hardware, wired to particular pins.</p>

----

## Nobody drives the line high

<img src="content/img/open-drain.svg" alt="Devices only pull the line low; a resistor pulls it high">

----

### Why it is built this way

If two chips talked at once, one pushing high and one pulling low, they would fight and something would burn out.

Since nothing ever pushes, the worst case is a garbled message.

----

## One whole message

<img src="content/img/i2c-frame.svg" alt="START, seven address bits, read/write bit, ACK, eight data bits, ACK, STOP" style="max-height:420px">

----

### The rule that makes it work

<img src="content/img/i2c-frame.svg" alt="START, seven address bits, read/write bit, ACK, eight data bits, ACK, STOP" style="max-height:286px">

<div class="two">
<div>

SDA may only change <strong>while SCL is low</strong>.

Every bit is set up during the low half, and read during the high half.

</div>
<div>

So a change on SDA <strong>while SCL is high</strong> cannot be data.

Those are reserved: falling means START, rising means STOP.

</div>
</div>

<p class="sub">Two signals, and that one rule, is the whole protocol.</p>

----

### Walking through it

<img src="content/img/i2c-frame.svg" alt="START, seven address bits, read/write bit, ACK, eight data bits, ACK, STOP" style="max-height:286px">

<div class="two">
<div style="font-size:.92em">

<span class="step">1.</span> <strong>START.</strong> SDA falls while SCL is high.

<span class="step">2.</span> <strong>Seven address bits.</strong> <code>0x76</code>, most significant first.

<span class="step">3.</span> <strong>One R/W bit.</strong> <code>0</code> for writing.

<span class="step">4.</span> <strong>ACK.</strong> The chip pulls SDA low to say it is there.

</div>
<div style="font-size:.92em">

<span class="step">5.</span> <strong>Eight data bits.</strong> Here <code>0xD0</code>, the register wanted.

<span class="step">6.</span> <strong>ACK.</strong> The chip acknowledges again.

<span class="step">7.</span> <strong>STOP.</strong> SDA rises while SCL is high.

<p class="sub">No ACK at step 4 means nothing is at that address.</p>

</div>
</div>

----

## The address and R/W are one byte

<img src="content/img/address-byte.svg" alt="Seven address bits plus the R/W bit make a single byte" style="max-height:420px">

----

### Why that matters

<div class="two">
<div>

The 7 address bits and the R/W bit are not two separate things on the wire. They are <strong>one byte</strong>, sent together.

<code>0x76</code> with R/W set to write is the byte <code>0xEC</code>.

The same address set to read is <code>0xED</code>.

</div>
<div style="font-size:.92em">

<div class="box warn">
<span class="lbl">Where this bites</span>
Some datasheets quote the 7-bit address, some quote the shifted byte.

If an address looks twice what you expected, that is why.
</div>

</div>
</div>

----

## So reading takes two messages

The message on the last slide ended in a STOP. It only told the chip which register was wanted.

<div class="two">
<div>

<h4>Message one</h4>

Address byte with R/W = <strong>write</strong>

Then <code>0xD0</code>, the register number.

<p class="sub">The chip remembers it.</p>

</div>
<div>

<h4>Message two</h4>

Address byte with R/W = <strong>read</strong>

Then the <strong>chip</strong> drives the eight data bits while the Arduino clocks them.

<p class="sub">The direction flips. Same wires.</p>

</div>
</div>

----

### Which is why the code has two halves

<div class="two">
<div>

```cpp
Wire.beginTransmission(0x76);
Wire.write(0xD0);
Wire.endTransmission();

Wire.requestFrom(0x76, 1);
byte value = Wire.read();
```

</div>
<div style="font-size:.86em">

The top three lines are message one. R/W is set to write because you called <code>beginTransmission</code>.

<code>requestFrom</code> is message two. R/W is set to read because you called that instead.

<p class="sub">You never set the R/W bit yourself. The call you choose sets it.</p>

</div>
</div>

----

## What you now know

| | |
|---|---|
| SDA and SCL | Data and clock. A4 and A5 |
| Open drain | Chips pull low, a resistor pulls high |
| START and STOP | SDA changing while SCL is high |
| Address frame | 7 bits, then a read/write bit |
| ACK | The chip pulling SDA low to confirm |
| Address byte | 7 address bits and R/W, sent as one byte |
| Reading a register | Two messages, not one |
